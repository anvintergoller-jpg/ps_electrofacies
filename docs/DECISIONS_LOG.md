# Журнал решений

## 2026-09-25. Архитектура

- **Мощности считаем в TVDSS (абсолютные отметки), не в MD.**
  Причина: инвариант к наклону ствола, корректная корреляция
  между скважинами.
- **Разметка точек каротажа — по MD.** Точки LAS приходят в MD.
- **Ось Y на графике — TVDSS.** Стандарт для корреляционных схем.
- **MD → TVDSS — линейная интерполяция** через таблицу `.dev`.
  Точность ~1 см, что достаточно.

## 2026-09-25. Нормализация

- **SP и GK нормализуем к [0, 1]** по перцентилям внутри рабочего
  интервала. 0 = чистый песок, 1 = чистая глина.
- **Перцентили 5 и 95** для опорных линий.
- **Рабочий интервал** = от первой кровли до конца `.dev`.
  Нормализация вне этого интервала — NaN.

## 2026-09-25. Классификация формы (v1.0)

- **Порог коллектора SP_norm < 0.6** (αПС > 0.4 по Муромцеву).
  Единый, без разделения на NTG и форму — чтобы не путаться.
- **Опорные точки** — средние по 15% мощности интервала
  (sp_top, sp_mid, sp_bot). Не фиксированное число точек.
- **Порог разницы верх/низ = 0.2.**
- **Пороги плато = 0.10, наклона = 0.20.**
- **Три подтипа трапеции** (top / bottom / middle) — новая категория.
- **Symmetric confidence** — разный по числу совпавших метрик:
  2 из 3 → 0.6, 3 из 3 → 0.85.
- **Микроинтервалы < 1 м** — присоединяются к соседним.

## 2026-09-25. Литологический профиль

- **5 корзин αПС** (по Муромцеву): глина, алевролит глинистый,
  алевролиты/пески, песчаник ср/з, песчаник кр/з.
- Считаем доли точек по каждой корзине на **сглаженной** кривой.
- Сумма = 1.0.

## 2026-09-25. Инструменты

- **Git + GitHub** для версионирования. Каждая значимая итерация —
  коммит.
- **Файлы результатов с timestamp** (`227_2263_features_2026-09-25_15-26-29.csv`),
  чтобы не перезаписывать и не спотыкаться о блокировки Excel.
- **Без ML** на первом этапе. Только правила, объяснимые геологу.

## 2026-09-26. ADR-001. Система типов формы — 6 базовых + uncertain

**Статус:** принято.
**Версия правил:** 2.0.

### Контекст

На шаге D.3 классификация формы аномалии ПС была формализована
в 8 типов по трём опорным точкам SP_norm (sp_top / sp_mid / sp_bot):
`bell`, `funnel`, `cylinder`, `symmetric`, `trapezoid-top`,
`trapezoid-bottom`, `trapezoid-middle`, `uncertain`.

Первые прогоны на пилотной скважине 227_2263 показали:

1. `trapezoid-top` и `trapezoid-bottom` практически не отличимы
   от `bell` и `funnel` по трём опорам — разница только в длине
   верхнего/нижнего плато, которая по трём точкам не измеряется.
2. `symmetric` и `v-shape` (плавная чаша vs острый угол) имеют
   одинаковые опоры и различаются только формой перехода.
3. Один признак `frac_core` (доля точек в узком коридоре вокруг
   `sp_mid`) частично разделяет `trapezoid-middle` / `symmetric` /
   `v-shape` / `cylinder`, но не устойчив на коротких интервалах
   (10–20 точек).
4. Тонкие переслаивания внутри интервала (песок–глина–песок)
   на этапе сегментации не разрезаются и попадают в классификатор
   как одна «аномалия» неопределённой формы.

### Решение

Система типов сокращена до **6**:

| Тип | Смысл |
|---|---|
| `bell` | глина сверху, песок снизу |
| `funnel` | песок сверху, глина снизу |
| `cylinder` | ровное плато на песчаном уровне |
| `trapezoid-middle` | песок в середине, глина по краям |
| `symmetric` | плавная чаша (парабола) |
| `uncertain` | не определено |

Убраны: `trapezoid-top`, `trapezoid-bottom`.
Не вводим отдельный `v-shape` — острые V-профили идут в `symmetric`
или `uncertain`.

**Переслаивание (M-форма)** — это не тип формы, а симптом ошибки
сегментации. Ловится только по опорам (sp_top и sp_bot в песчаной
зоне, sp_mid — в глинистой). Функция `_has_multiple_minima`
оставлена в коде, но отключена от логики — вернёмся, когда будем
дорабатывать сегментацию.

### Последствия

- 4 разных типа на 7 коллекторных интервалах пилота.
- Все интервалы классифицируются, эталоны рисуются на планшете.
- Часть интервалов отнесена к формам, не совпадающим с ручной
  интерпретацией. Это ожидаемо и зафиксировано в ADR-002.

### Файлы, затронутые решением

`docs/CLASSIFICATION_RULES.md` (→ версия 2.0),
`src/domain/classify_form.py` (→ `RULES_VERSION = "2.0"`),
`src/visualization/form_legend.py` (6 панелей + резерв),
`src/domain/reference_curve.py`,
`config/config.yaml`.

## 2026-09-26. ADR-002. Доработка критериев классификации — отложена

**Статус:** принято (временное решение).
**Триггер возврата:** после шага G (типизация разреза по скважине),
при накоплении ≥ 5 скважин с ручной разметкой.

### Контекст

После ADR-001 мы провели несколько итераций уточнения критериев
на **одной** пилотной скважине. Каждая итерация решала один-два
случая, но:

- ломала другие;
- требовала признаков, которых пока нет (форма кривой по всей
  длине, а не по трём точкам);
- приводила к подгонке порогов под конкретные интервалы одной
  скважины (overfitting).

Попытка разделить `trapezoid-middle` / `symmetric` / `v-shape`
через `frac_core` оказалась неустойчивой на коротких интервалах
(10–20 точек). Тонкие переслаивания не ловятся ни опорами,
ни `frac_core`.

### Решение

Прекращаем тонкую настройку критериев на одной скважине.
Фиксируем `RULES_VERSION = "2.0"` как рабочую версию.

Пороги в `config.yaml` оставляем как есть:
`threshold_diff: 0.20`, `slope_threshold: 0.20`,
`plateau_threshold: 0.10`, `core_threshold: 0.05`,
`frac_core_trapezoid: 0.40`, `frac_core_v_shape: 0.15`.

Продолжаем движение по роадмапу — к шагам E, F, G.

### Обоснование

Классификация формы — задача, требующая обучающей выборки.
Одна скважина не даёт разнообразия форм, чтобы отличить системные
ошибки от случайных и откалибровать пороги.

«По-настоящему» формализация возможна при наличии:

1. **≥ 5 скважин** с одинаково обработанными кривыми.
2. **Ручной разметки** 20–30 интервалов геологом.
3. Понимания, какие типы ошибок встречаются системно
   (не «9-1 неверно», а «все M-формы валятся в bell»).

### План возврата

1. Собрать 5+ скважин в единый пайплайн (шаг H).
2. Экспортировать `intervals.csv` по всем скважинам.
3. Дать геологу разметить форму вручную (Excel).
4. Сравнить с текущими результатами, найти системные ошибки.
5. Пересобрать критерии под реальные данные.
6. При 30+ скважинах с разметкой — рассмотреть ML.

### Что НЕ делаем сейчас

- Не крутим пороги «на глаз».
- Не добавляем новые типы (`v-shape`, M-форма и т. п.).
- Не расширяем признаки (кривизна, сплайны, спектры).
- Не трогаем `classify_form.py` до возврата к теме.

## 2026-09-26. Положение интервала — часть общей типизации

- **Помимо размера и формы, важный признак — положение интервала
  в пласте-контейнере.** Уже описано в `docs/FEATURES.md`, §5.4,
  но потерялось в роадмапе. Возвращаем в план (шаг E).
- **Формально:** `centroid_relative` — доля от кровли до подошвы
  контейнера, 0 = кровля, 1 = подошва.
- **Категория** (`position_in_container`):
  - `top`: `centroid_relative < 0.33`
  - `middle`: `0.33 ≤ centroid_relative ≤ 0.67`
  - `bottom`: `centroid_relative > 0.67`
- **Зачем:** тип разреза (шаг F) и типизация разреза по скважине
  (шаг G) будут опираться на связку «форма + размер + положение».
  Например, «крупный колокол в кровле пласта» и «мелкий колокол
  в подошве» — это разные элементы разреза.
- **Считаем на шаге E** вместе с размером: обе характеристики —
  атрибуты коллекторного интервала, вычисляются из уже
  имеющихся данных (`thickness_tvdss`, границы контейнера,
  `depth_tvdss` точек).

## 2026-09-26. Шаг E — размер и положение интервала

**Статус:** принято.

### Контекст

Помимо формы, для сводной типизации пласта нужны две
характеристики каждого коллекторного интервала:

- **размер** — крупный он или мелкий,
- **положение** — где он сидит в родительском пласте.

Обе считаются из уже имеющихся данных (`thickness_tvdss`,
`top_tvdss`, `bottom_tvdss`, `depth_tvdss` точек), отдельных
измерений не требуется.

### Решение

**Размер (`size_class`)** — по ДОЛЕ интервала в мощности
родительского пласта-контейнера:
relative = thickness_interval_tvdss / thickness_container_tvdss
small: relative < 0.33
medium: 0.33 .. 0.67
large: relative > 0.67

Пороги **фиксированные**, не перцентили выборки. Причина: размер
должен быть **сопоставим между скважинами для одного и того же
пласта**. Перцентили внутри одной скважины давали бы «large» почти
для любого интервала, если в скважине всего 2–3 коллектора. Доля
от мощности контейнера — величина, не зависящая от выборки.

**Положение (`position_in_container`)** — по относительному
положению центроида интервала в пласте:
centroid_relative = (top_container − centroid_tvdss)
/ (top_container − bottom_container)
top: < 0.33
middle: 0.33 .. 0.67
bottom: > 0.67

Пороги **тоже фиксированные**, по смыслу — деление мощности
пласта на три равные части.

### Почему пороги фиксированные, а не перцентили

На шаге E мы сначала попробовали перцентили выборки — но быстро
увидели проблему: они дают **произвольный** результат, зависящий
от того, сколько интервалов в скважине. При 3 интервалах «large»
получит 1 из них, при 30 — 10. Сравнить «крупный интервал БС9
в скв.1» с «крупным интервалом БС9 в скв.2» по таким категориям
нельзя.

Фиксированные пороги дают однозначное правило: интервал, занимающий
40% мощности пласта, — **всегда** `medium`, независимо от того, что
ещё есть в этой скважине.

### Побочный эффект

На пилоте 227_2263 получилось распределение:
- по размеру: 6 small, 1 medium, 0 large;
- по положению: 6 top, 1 bottom, 0 middle.

Это **не ошибка**, а реальная картина на одной скважине. Коллекторы
занимают малую долю мощности пластов, и почти все сидят в верхней
трети своих контейнеров. Категория `large` появится, когда в выборке
будут пласты, где коллектор занимает > 67% мощности, а `middle` —
когда интервалы окажутся в средней трети. На одной скважине — это
нормально.

### Особенности реализации

- `centroid_tvdss` — **среднее по точкам**, а не середина по границам.
  Устойчивее для интервалов с неравномерным распределением точек.
- `size_class = n/a` для `non_reservoir` (форма и размер — только
  у коллекторов).
- `size_class = unknown` для reservoir, если контейнер не найден
  в `layers` (нет границ).

### Файлы, затронутые решением

- `src/domain/size_class.py` — новый модуль.
- `config/config.yaml` — секция `size_classification`.
- `src/run_pipeline.py` — шаг 7c между классификацией формы
  и признаками пласта.
- `docs/FEATURES.md` — §5.4 (положение) и §7 (размер)
  считаются реализованными.
  ## 2026-09-28. ADR-003. Единица анализа — пласт-контейнер, а не разрез

**Статус:** принято.

### Контекст

Изначальный план (шаг G) предполагал ещё один уровень типизации —
**разрез скважины целиком**: последовательность типов пластов
сверху вниз и общая характеристика скважины
(«регрессивный разрез», «трансгрессивный разрез» и т. п.).

При обсуждении выяснилось, что этот уровень **не нужен** для
конечной задачи проекта.

### Решение

**Единица анализа — пласт-контейнер** (БС9, БС10-1, БС10-2, …).

Все характеристики (форма, размер, положение, NTG, мощность)
относятся к **конкретному пласту в конкретной скважине**.

Типизация разреза скважины целиком **не делается** —
шаг G отменяется. Его смысл (агрегация выше уровня интервала)
полностью реализуется шагом F, но на уровне пласта.

При работе с выборкой скважин сопоставляются **одноимённые
пласты между скважинами**, а не разрезы целиком:

- не «скв.1 похожа на скв.2»,
- а «БС9 в скв.1 похож на БС9 в скв.2».

### Обоснование

1. **Конечная цель — картирование по пластам.** Мы хотим построить
   карту, например, «тип БС9 по площади». Разрез скважины тут
   не помогает.
2. **Одноимённые пласты — естественный объект сопоставления.**
   Геолог ставит одинаковые отбивки БС9 в разных скважинах именно
   для того, чтобы сравнивать один и тот же стратиграфический
   уровень.
3. **Разрез как единица — избыточная информация.** Метаданные
   «в скважине А после БС9 идёт БС10-1» — это справочная
   информация, не типизация. Её можно восстановить при
   необходимости из сортировки по глубине.
4. **Меньше кода и меньше сущностей.** Одна таблица
   `features.csv` (строка на пласт) вместо двух (пласты + разрезы).

### Последствия

- Шаг G отменён. Нумерация: F, H (G теперь занят H).
- Работа с несколькими скважинами (шаг H) — это матрица
  «скважина × пласт», где строки — уникальные пласты
  (БС9, БС10-1, …), столбцы — скважины.
- Кластеризация на шаге H — кластеризация **пластов**, не разрезов.
- В `FEATURES.md` §6 уточнён: сводная типизация —
  на уровне пласта, без промежуточного уровня «разрез».

### Файлы, затронутые решением

- `docs/ROADMAP.md` — шаг G убран, F — финальный шаг типизации.
- `docs/FEATURES.md` — §6 (сводная типизация пласта).
- `docs/PROJECT_STATE.md` — дорожка дальше.
- `src/domain/container_type.py` — новый модуль (в рамках F).
- `src/domain/features.py` — расширяется NTG и агрегатами.

## 2026-09-28. ADR-004. Формат сводной типизации пласта (шаг F)

**Статус:** принято.

### Контекст

Шаг F собирает все признаки по пласту в одну строку. Нужно было
определить:

- как считать «доминирующую» характеристику (форму, размер,
  положение);
- какой формат итоговой метки и расширенного описания;
- где хранить результат;
- как обрабатывать `uncertain` и отсутствие коллекторов.

### Решение

**Доминирующая характеристика — по суммарной мощности.** Если
две топ-характеристики имеют разницу суммарных мощностей **менее
10% от общей мощности резервуаров пласта** — берём ту, у которой
выше `mean_confidence`. Иначе — по мощности.

**Формат вывода — комбинация короткой метки и расширенного
описания:**

| Колонка | Что |
|---|---|
| `container_type` | короткая метка `{single/multi/no-sand}-{form}-{size}-{position}` |
| `container_summary` | текст: `N пропластков: bell medium top (6.66 м); …` |
| `container_intervals_json` | JSON-массив `[{"form": "bell", "size": "medium", "position": "top", "thickness": 6.66}, …]` |

**Порог no-sand:** NTG = 0 (нет коллекторов — нет типа).

**`uncertain`** участвует в голосовании по мощности как обычная
форма. Если все интервалы `uncertain` — пласт тоже получает
`container_type` с формой `uncertain`.

**Хранение:** всё в `features.csv` (одна строка на пласт).
Отдельный файл не создаём.

### Обоснование

1. **Мощность как главный критерий** — геологически осмысленно:
   если 70% коллектора в пласте — колокол, то пласт «колокольный».
2. **Confidence как тай-брейк при близости** — использует
   дополнительную информацию, но не подменяет мощность.
3. **Три представления метки** — гибкость: короткая метка для
   глаз, summary для чтения, JSON для машинной обработки.
4. **Единый файл `features.csv`** — не плодим сущности.

### Файлы, затронутые решением

- `src/domain/container_type.py` — новый модуль.
- `src/domain/features.py` — NTG + агрегаты.
- `src/run_pipeline.py` — шаг 7d (после 7c).
- `config/config.yaml` — секция `container_type`.
